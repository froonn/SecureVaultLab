# Отчёт по оценке защищённости приложения `lw2_1`

Объект оценки: веб-приложение SecureVaultLab (FastAPI + Jinja2 + SQLite + Nginx + Docker), реализующее регистрацию, аутентификацию, публичные и конфиденциальные записи, административные функции.

Вид аудита: статический анализ исходного кода и конфигураций репозитория. Динамические тесты (DAST, пентест) не запускались. Оценки риска contextual — для учебного стенда.

---

## 1. Методика оценки защищённости

### 1.1. Цель и принципы

Цель — определить фактический уровень защищённости приложения, выявить уязвимости и несоответствия политикам, оценить риск и сформировать план устранения. Принципы: законность и наличие разрешения, ограничение scope, воспроизводимость, приоритет риска, defence-in-depth, least privilege, разделение сред, сохранение доказательств.

### 1.2. Этапы

| Этап | Содержание | Результат |
|---|---|---|
| 0. Подготовка | Согласование scope, границ, окон тестирования; инвентаризация активов; правила работы с данными | Паспорт аудита, перечень активов |
| 1. Архитектура и данные | DFD-модель, trust boundaries, потоки данных, классификация информации | Схема компонентов и данных |
| 2. Модель угроз | STRIDE/LINDDUN, сценарии атак, нарушители, поверхности атаки | Реестр угроз |
| 3. Проверка политик | ОС/контейнеры, компоненты приложения, сеть, конфиденциальность | Чек-лист соответствия |
| 4. Инструментальный анализ | SAST, SCA, поиск секретов, IaC/container scan, DAST, TLS-скан | Отчёт сканеров |
| 5. Ручной аудит | Код, конфигурации, authn/authz, сессии, CSRF, XSS, IDOR, логирование | Подтверждённые находки |
| 6. Оценка риска | Вероятность × ущерб, CVSS, критичность актива | Приоритизированный реестр |
| 7. Отчёт | Описание, доказательства, влияние, рекомендации, сроки | Отчёт и план remediation |
| 8. Повторная проверка | Retest, регрессия, контроль остаточного риска | Акт закрытия |

### 1.3. Домены оценки

- **ОС и контейнеры:** пользователи, права файлов, сервисы, SELinux/AppArmor, seccomp, capabilities, ресурсы, обновления, Docker daemon.
- **Компоненты приложения:** аутентификация, пароли, сессии, CSRF, RBAC, криптография, секреты, аудит, обработка ошибок, целостность.
- **Сеть:** TLS, публикуемые порты, сегментация, прокси-заголовки, rate limiting, WAF/IDS, egress.
- **Конфиденциальность:** классификация данных, шифрование в покое и в пути, управление ключами, PII в логах, retention, резервные копии, права субъектов данных.

### 1.4. Шкала и критерии приёмки

Риск = вероятность × ущерб (матрица 5×5): Critical 20–25, High 12–19, Medium 6–11, Low 1–5. Дополнительно — CVSS 3.1/4.0. Критерии приёмки: отсутствие Critical/High; соответствие OWASP ASVS Level 2; TLS не ниже A по testssl.sh; отсутствие секретов в репозитории; успешный retest.

### 1.5. Инструменты

Semgrep/Bandit/CodeQL, gitleaks/trufflehog, pip-audit/OSV-Scanner/Trivy/Grype, Checkov/hadolint/docker-bench-security, OWASP ZAP/Burp/Nuclei, testssl.sh/sslyze, Lynis/OpenSCAP, Falco/auditd. Базовые требования: OWASP Top 10, OWASP ASVS, CIS Docker Benchmark, NIST SP 800-115, PTES, ГОСТ Р ИСО/МЭК 27001/27002, ГОСТ Р 56939.

## 2. Анализ приложения

### 2.1. Политика безопасности ОС и контейнеров

**Что сделано хорошо:** контейнер приложения работает от непривилегированного пользователя `app`, заданы `cap_drop: ALL`, `no-new-privileges:true`; Fernet-ключ вынесен в Docker secret; каталог `/data` отделён; Nginx скрывает версию (`server_tokens off`); SQLite работает в WAL с `foreign_keys=ON` и `busy_timeout`.

**Находки:**

| ID | Находка | Риск | Подтверждение |
|---|---|---|---|
| OS-1 | Порт `8080` публикуется на все интерфейсы и работает без TLS/редиректа, при этом приложению принудительно сообщается `X-Forwarded-Proto: https`. Пароли и сессии могут передаваться в открытом виде; возможен обход TLS-периметра | **High** (Critical при доступе из недоверенной сети) | `docker-compose.yml:37-39`, `nginx/nginx.conf:36-69` |

| OS-4 | Нет `read_only` rootfs, лимитов CPU/RAM/PIDs, tmpfs для `/tmp`; у Nginx нет `cap_drop`; не заданы кастомные seccomp/AppArmor-профили | **Medium** | `docker-compose.yml:18-28,47-48` |
| OS-5 | Базовые образы закреплены тегами, а не digest; Poetry устанавливается через `curl … \| python3 -` без проверки контрольной суммы | **Medium** | `Dockerfile:1,18` |

### 2.2. Политика безопасности компонентов и их взаимодействия

**Что сделано хорошо:** Argon2id с параметрами `time=3, memory=64 MiB, parallelism=2`; серверные сессии, в БД хранится SHA-256 токена; регенерация сессии при логине (session fixation); CSRF-токен с HMAC; ORM вместо конкатенации SQL; проверка владельца записей (anti-IDOR); Jinja2 autoescape; RBAC `user/admin`; блокировка неактивных пользователей проверяется на каждом запросе; аудит ключевых действий.

**Находки:**

| ID | Находка | Риск | Подтверждение |
|---|---|---|---|
| APP-1 | `TrustedHostMiddleware` содержит `"*"` — защита от Host header injection фактически отключена | **Medium** | `app/main.py:37` |
| APP-2 | `get_client_ip()` безусловно берёт первый `X-Forwarded-For`, который контролируется клиентом. IP в сессиях и аудите можно подделать | **Medium** | `app/deps.py:15-19` |
| APP-3 | Регистрация не ограничена rate limit, но вызывает дорогой Argon2 (64 MiB). Возможен DoS исчерпанием памяти/CPU; длина пароля на уровне формы/сервиса не ограничена сверху (до 1 МБ тела) | **High** | `nginx/nginx.conf:48`, `app/services/users.py:27-33` |
| APP-4 | Анонимная сессия создаётся и коммитится в БД на **каждый** запрос без cookie, включая `/healthz` (Docker healthcheck каждые 10 с), 404 и сканеры. Очистки просроченных сессий нет — неограниченный рост SQLite и disk exhaustion | **High** | `app/main.py:40-55`, `app/security/sessions.py:44-55` |
| APP-5 | Дефолтный `APP_SECRET_KEY = "change_me"`; фактически ключ не используется, но создаёт ложное чувство защиты. Fernet-ключ единственный, без версии/ротации | **Medium** | `app/config.py:15`, `app/security/crypto.py:5`, `.env:2` |

| APP-7 | Нет MFA, lockout/прогрессивной задержки, смены пароля через интерфейс и отзыва всех сессий при смене пароля; нет проверки паролей по базам утечек | **Medium** | `app/services/users.py:60-73,100-108`, отсутствие роутов |
| APP-8 | Любой контейнер в `app_net` может обратиться к FastAPI напрямую, минуя Nginx (TLS, заголовки, rate limit). Нет mTLS/allowlist между Nginx и приложением | **High** | `docker-compose.yml:13-16,45-46`; `nginx/nginx.conf` |
| APP-9 | README заявляет JSON API и CSRF-заголовки, но `app/routers/api/*` пусты — документация не соответствует реализации; оценка только по коду | **Info/Medium** | `app/routers/api/*.py` |
| APP-10 | Username уникален с учётом регистра (SQLite BINARY), возможны `Admin`/`admin`; email нормализуется, username — нет | **Low/Medium** | `app/models.py:38`, `app/services/users.py:41-45` |
| APP-11 | `/docs` и `/openapi.json` включены в `dev`; `.env` содержит `APP_ENV=dev` | **Low** | `app/main.py:28-34`, `.env:1` |
| APP-12 | Нет миграций (Alembic не используется), схема создаётся `create_all`; нет тестов и CI-проверок безопасности | **Medium** | `app/main.py:22-25`, пустой `tests/` |

### 2.3. Сетевая политика безопасности

**Что сделано хорошо:** TLS 1.2/1.3, HTTPS на 8443, HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, CSP, `limit_req` для логина и `/api/`, таймауты проксирования, `server_tokens off`.

**Находки:**

| ID | Находка | Риск | Подтверждение |
|---|---|---|---|
| NET-1 | `8080` — открытый HTTP-вход без редиректа на HTTPS; приложению ложно сообщается, что схема `https`. Это главный сетевой дефект | **High** | `nginx/nginx.conf:32-69` |
| NET-2 | Самоподписанный сертификат `CN=localhost` без SAN, пользователей просят принять исключение; HSTS с недоверенным сертификатом не работает | **Medium** | `README.md:142-153,194-196` |

**Что сделано хорошо:** содержимое конфиденциальных записей шифруется Fernet (AES-128-CBC + HMAC-SHA256), ключ вне БД, доступ только владельцу; пароли — Argon2id; токены сессий в БД хешированы; SQL-инъекции и XSS в шаблонах закрыты.

**Находки:**

| ID | Находка | Риск | Подтверждение |
|---|---|---|---|
| DATA-1 | Шифруется только `content`; `title`, email, username, IP, User-Agent, аудит и метаданные — открытым текстом. БД в целом не зашифрована | **Medium** | `app/models.py:78-89,92-103` |
| DATA-2 | Fernet-ключ и БД находятся на одном хосте: компрометация хоста даёт и шифротекст, и ключ. Нет KMS/HSM, отдельного key server | **High** | `secrets/fernet_key`, `data/app.db` |
| DATA-3 | Нет ротации/версионирования ключей; смена ключа сделает старые записи нечитаемыми. Нет процедуры re-encrypt | **Medium** | `app/security/crypto.py` |
| DATA-4 | Нет `Cache-Control: no-store` для аутентифицированных и конфиденциальных страниц — браузер/прокси могут кэшировать данные | **Medium** | `app/main.py:64-81`, `app/routers/html/_common.py` |

## 3. Комплекс мер по усовершенствованию

### P0 — до любого использования вне изолированного стенда

1. **Убрать/закрыть HTTP-вход.** Удалить публикацию `8080` или привязать к `127.0.0.1`; на 8080 сделать редирект на HTTPS; не подменять `X-Forwarded-Proto` без доверенного прокси. Публиковать только `127.0.0.1:8443:8443`.
2. **Исправить права.** `chmod 700 secrets data logs nginx/certs`, `chmod 600 data/app.db* .env secrets/fernet_key`; `umask 077`; ключ и БД — на разных носителях/хостах.
3. **Заменить секреты.** Убрать дефолтные значения, валидировать `APP_SECRET_KEY`/Fernet-ключ при старте, не хранить пароли в CLI/history.
4. **Закрыть Host/XFF.** `allowed_hosts` — только реальные имена; Nginx должен **перезаписывать** `X-Forwarded-For` (`$remote_addr`), а приложение — доверять заголовку только от Nginx.
5. **Устранить DoS.** Исключить `/healthz`, `/favicon.ico`, `/static` из создания сессий; добавить очистку просроченных/анонимных сессий; rate limit на register и login per-IP+per-account; max длина пароля 128, `q` — 200; лимиты CPU/RAM/PIDs.
6. **Исправить CSP и кэш.** Вынести inline-стили/JS или использовать nonce/hash; добавить `base-uri 'self'; form-action 'self'; frame-ancestors 'none'; object-src 'none'`; для чувствительных страниц — `Cache-Control: no-store`.
7. **Изолировать сеть.** Две сети: edge (Nginx) и internal (app+БД), `internal: true`; закрыть egress; mTLS или unix-socket между Nginx и app; `read_only: true`, tmpfs `/tmp`, `cap_drop` для Nginx.
8. **Усилить аудит.** Отдельное append-only хранилище/поток, hash-chain, транзакционная запись, логирование отказов authz/CSRF, retention и алерты.

### P1 — 2–6 недель

- MFA для администраторов, отдельная учётная запись администратора, re-auth на опасные операции, запрет блокировки других админов без superadmin.
- Смена пароля с отзывом всех сессий, lockout/backoff, проверка паролей по утечкам, password manager.
- Шифрование метаданных/БД (SQLCipher или full-disk encryption), KMS/HSM, key rotation с версией ключа и re-encrypt.
- Реальный TLS-сертификат с SAN, автоматическое обновление, современные cipher suites, OCSP stapling; HSTS только после валидного сертификата.
- WAF (ModSecurity CRS), IDS/IPS, централизованные логи, SIEM, Falco/auditd, алерты на brute force и админские действия.
- Шифрованные бэкапы, проверка restore, retention и удаление PII; политика конфиденциальности, DPIA, права субъектов данных.
- SCA/SAST/secrets/IaC-сканеры в CI, pin digest образов, отказ от `curl | python`, удаление неиспользуемых зависимостей (`slowapi`, `itsdangerous`, `email-validator`, `alembic` при отказе от миграций).
- Тесты безопасности: authz/IDOR, CSRF, XSS, session fixation, rate limit, загрузка больших тел.

### P2 — постоянное улучшение

- Регулярный pentest и threat model review; метрики MTTR, покрытие контролей, количество открытых High/Critical.
- HA/резервирование, мониторинг доступности, chaos-тесты, обучение пользователей.
- CIS Benchmark для хоста и Docker, rootless Docker/userns-remap, SELinux в `Enforcing` с корректными контекстами (без `setenforce 0`).

**Критерии завершения:** 0 Critical/High; ASVS L2; TLS A; секреты не в git и не в CLI; healthcheck не создаёт записи; retest подтверждает исправления.

## 4. Рекомендации по безопасному использованию

**Пользователям:**

- Работать только через `https://localhost:8443`; не использовать `http://…:8080`.
- Проверять сертификат/отпечаток; не принимать исключение для незнакомого хоста.
- Использовать уникальный пароль и менеджер паролей; не хранить в учебном приложении реальные секреты, персональные данные и документы.
- Выходить из системы, не оставлять сессию на общих устройствах, не работать в публичных Wi-Fi без доверенного туннеля.
- Не открывать подозрительные ссылки и не вводить учётные данные на страницах, открытых не через штатный вход.

**Администраторам/операторам:**

- До первого запуска заменить все секреты, ключ Fernet хранить отдельно от БД, делать шифрованные бэкапы и проверять восстановление.
- Запускать только в `APP_ENV=prod`, без `/docs`, с реальным TLS-сертификатом; закрыть 8080/ngrok, ограничить порты loopback и firewall.
- Не передавать пароли аргументами CLI; использовать интерактивный ввод/секреты Docker.
- Принцип наименьших привилегий: отдельные учётные записи, MFA для админов, регулярная ротация ключей и паролей, мониторинг аудита.
- Своевременно обновлять образы/зависимости, сканировать их, не отключать SELinux; применять CIS Docker Benchmark.
- При инциденте: отозвать все сессии, заблокировать учётные записи, ротировать TLS- и Fernet-ключи с перешифрованием, сохранить логи, восстановить чистый бэкап, уведомить ответственных.

## 5. Итоговая оценка

Базовая защита приложения выстроена грамотно: Argon2id, серверные сессии с хешированием токенов, ротация при логине, CSRF, ORM, проверка владельца, autoescape, шифрование конфиденциального содержимого, контейнерные ограничения. Однако **deployment-уровень содержит существенные дефекты**: открытый HTTP-порт 8080, слабые права на БД/`.env`, wildcard в `TrustedHost`, подделываемый `X-Forwarded-For`, DoS через регистрацию и «раздувание» сессий healthcheck-ом, отсутствие лимитов и полноценной сетевой изоляции. В текущем виде приложение пригодно только как изолированный учебный стенд; после устранения P0 риск снижается до приемлемого Medium, после P1 — до уровня, допускающего ограниченную эксплуатацию.

> **Примечание:** разделы 1–5 выше — первоначальный статический аудит. Актуальный статус находок и результаты динамической перепроверки — в разделе 6.

## 6. Динамический retest и устранение (2026-11-07)

В отличие от первоначального статического аудита, на этом этапе выполнена **динамическая перепроверка** против рабочего стенда (`https://<SERVER_IP>:8443`, ветка `security-hardening`), а также исправлена часть оставшихся находок на уровне кода.

### 6.1. Подтверждено динамически — контроли работают

| Проверка | Метод | Результат |

| Подмена IP (`X-Forwarded-For`/`X-Real-IP`) | POST `/auth/login` с подставными заголовками → чтение `audit_log` | записан реальный IP клиента, не подставной — подмена закрыта |
| Строгий CSP / HSTS | заголовки ответа на 8443 | `default-src 'self'` без `unsafe-inline`, HSTS присутствует |

| Закрытие 8080 снаружи | TCP-connect на публичный `:8080` | соединение отклонено (bind `127.0.0.1`) |
| Флаги cookie | `Set-Cookie` сессии | `HttpOnly; Secure; SameSite=lax` |
| Контроль доступа | unauth-доступ к `/confidential`, `/admin/users` | 401; `/public/new` → 303 на логин |

Полная остаточная картина — в разделах 2–3.

### 6.5. Обновлённая оценка

Ядро безопасности (authn/authz, сессии, CSRF, IDOR, крипто, отсутствие SQLi/XSS) подтверждено и статически, и динамически — пробить не удалось. Конфиг-дефекты периметра, отмеченные как критичные в первоначальном отчёте, на рабочем стенде закрыты, что подтверждено динамически. Остаточный риск сосредоточен в инфраструктуре хоста и операционных процессах (права файлов, сетевая изоляция, управление ключами, бэкапы, мониторинг), а не в коде приложения. Для учебного стенда с объявленным scope уровень защищённости приложения оценивается как **приемлемый**; для продакшн-эксплуатации необходимо закрыть оставшиеся пункты раздела 6.4.
